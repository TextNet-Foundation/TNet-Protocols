# TNet Protocols Specification — Version 2.0

This document specifies the three core protocols of **TNet**, a decentralized text network:

- **UTNP** — Universal Text Negotiation Protocol
- **TMUTP** — TMkUp Transfer Protocol
- **TBIP** — TNet Binary Information Protocol

All three protocols operate over TCP. UTNP is used for service discovery, protocol negotiation, and discovery of other UTNP nodes. TMUTP transfers TMkUp documents, while TBIP transfers binary resources.

---

## 1. Common Protocol Rules

### 1.1. Protocol Versions

Protocol versions are written in the first line of each request and response:

```text
UTNP/2.0
TMUTP/2.0
TBIP/2.0
```

A protocol version identifies the version of the protocol spoken on that connection. The version of a protocol selected through UTNP is negotiated separately from the UTNP version itself.

### 1.2. Transport

The protocols use TCP. The default ports are:

| Protocol | Default port |
|----------|--------------|
| `utnp`   | `34`         |
| `tmutp`  | `100`        |
| `tbip`   | `81`         |

A server may listen on a different port and advertise that port through UTNP.

### 1.3. Text Encoding and Message Layout

Protocol command lines and headers are textual. Implementations must use UTF-8 for textual values. Header names are case-insensitive. Header values are interpreted according to the header definition.

A request or response consists of a start line, zero or more header lines, an empty line separating the headers from the body, and an optional body:

```text
<protocol start line>
<Header-Name>: <value>
<Another-Header>: <value>

<body>
```

All headers belong in the header section, before the empty line. Protocol metadata must not be appended after the body.

`Content-Length` is measured in bytes, not characters. For a response with a body, the receiver reads exactly the number of bytes specified by `Content-Length`.

### 1.4. TNet Status Codes

TMUTP and TBIP use the common **TNet Status Codes** table. A status code has the same meaning in both protocols unless a protocol section explicitly limits its use.

| Code | Name | Description |
|------|------|-------------|
| `20` | `OK` | Successful response with content or data |
| `21` | `MOVED` | The requested resource has moved |
| `22` | `OK EMPTY` | Successful response with an empty body |
| `23` | `MULTIPLE CHOICES` | Multiple variants are available |
| `30` | `BAD REQUEST` | The request is invalid or malformed |
| `31` | `NOT FOUND` | The requested document or resource was not found |
| `32` | `FORBIDDEN` | Access to the requested resource is denied |
| `40` | `SERVER ERROR` | An internal server error occurred |
| `41` | `NOT IMPLEMENTED` | The requested method or functionality is not implemented |
| `42` | `SERVICE UNAVAILABLE` | The service is temporarily unavailable |
| `50` | `METHOD NOT ALLOWED` | The requested method is not allowed |
| `51` | `VERSION NOT SUPPORTED` | The requested protocol version is not supported |
| `52` | `INVALID RANGE` | The Range request is malformed or invalid |
| `53` | `RANGE NOT SATISFIABLE` | The requested range cannot be satisfied by the source resource |
| `54` | `UNSUPPORTED RANGE` | The requested range form or range unit is not supported |
| `55` | `REQUIRE SECURE` | The server requires a protected connection |

UTNP uses its own textual error responses rather than the numeric TNet Status Codes.

### 1.5. Compression Negotiation

TMUTP and TBIP support optional response compression negotiation.

A client may send the following request header to list the compression algorithms it can decode:

```text
Accept-Compression: <algorithm1>,<algorithm2>,...
```

A server may report the algorithms it supports with:

```text
Supported-Compression: <algorithm1>,<algorithm2>,...
```

If the server compresses the response body, it must identify the algorithm actually used with:

```text
Content-Encoding: <algorithm>
```

The algorithm selected for a response must be supported by the server and accepted by the client. If the request does not contain `Accept-Compression`, or if there is no mutually supported algorithm, the response body is sent without compression and `Content-Encoding` is omitted.

The order of algorithms in `Accept-Compression` expresses the client's preference. No particular compression algorithm is mandatory in this specification. An implementation must not use an algorithm that the client did not advertise as acceptable.

`Content-Length` describes the number of bytes actually transmitted in the response body, after compression when compression is used.

### 1.6. Secure Connections

UTNP, TMUTP, and TBIP can be used over a protected or an unprotected TCP connection. The server may accept any supported combination of:

- TLS handshake;
- SSH handshake;
- an unencrypted protocol request.

These connection types use the same TCP port for the respective protocol. A server must not require a separate port solely because the client uses TLS or SSH. The server distinguishes the connection type from the initial handshake or protocol data.

The client and server apply their own security policies. A client should prefer a protected connection. A server may require a protected connection and reject an unencrypted request.

UTNP reports supported protected transports using the `Security` header. Its value is a comma-separated list, for example:

```text
Security: tls,ssh
```

The header is informational: it reports security mechanisms associated with the advertised service, but it does not itself select a mechanism or replace the handshake. The client chooses the connection method according to its own policy, and the server accepts or rejects the actual handshake according to its capabilities and policy. A client may attempt a mechanism even when it is not listed in `Security`; successful establishment depends on whether the server accepts it.

`Security` lists protected mechanisms only. Unencrypted operation is not represented by a `none` value.

When a server requires a protected connection:

- UTNP returns `UTNP/2.0 ERROR REQUIRE SECURE` if the UTNP request itself is unencrypted.
- TMUTP or TBIP returns status `55 REQUIRE SECURE` if the request is unencrypted.

A client must not silently downgrade to an unencrypted connection when its own security policy forbids it.

## 2. UTNP — Universal Text Negotiation Protocol

**Version:** `2.0`  
**Default port:** `34`  
**Transport:** TCP  
**Purpose:** Service discovery, protocol-version negotiation, and discovery of other UTNP nodes. UTNP does not transfer documents or binary content and is not used as a content URL scheme.

### 2.1. Requests

UTNP/2.0 defines three commands:

```text
UTNP/2.0 NEGOTIATE <protocol>
UTNP/2.0 LIST
UTNP/2.0 EXPLORE
```

`NEGOTIATE` requests exactly one protocol name. A request must not contain a comma-separated list of protocol names.

For `NEGOTIATE`, the client sends the versions of the requested protocol that it supports:

```text
UTNP/2.0 NEGOTIATE tmutp
Supported-Versions: 1.0,2.0
```

`Supported-Versions` is a comma-separated list of versions supported by the client for the requested protocol.

`LIST` requests the list of protocols available from the server:

```text
UTNP/2.0 LIST
```

`EXPLORE` requests the list of UTNP nodes known to or recommended by the server:

```text
UTNP/2.0 EXPLORE
```

### 2.2. Successful Negotiation Response

When the requested protocol is available and a compatible version is found, the server responds with:

```text
UTNP/2.0 START PROTOCOL <name> <version> <host> <port>
Security: <mechanism1>,<mechanism2>,...
```

Example:

```text
UTNP/2.0 START PROTOCOL tmutp 2.0 example.com 100
Security: tls,ssh
```

The response identifies:

- the selected protocol name;
- the selected protocol version;
- the host where the protocol is available;
- the TCP port where the protocol is available;
- the protected transport mechanisms advertised for that service, through `Security`.

The server selects a protocol version supported by both the client and the server. If more than one version is compatible, the server selects the highest mutually supported version. The order of entries in `Supported-Versions` does not change this rule.

`Security` is a list, not a single selected transport. The client is not required to treat the first item as the only permitted choice.

### 2.3. Protocol List Response

For `LIST`, the server responds with `AVAILABLE`. Each protocol entry contains its name, version, host, and port. A `Security` header immediately following an entry describes the protected transports advertised for that entry.

```text
UTNP/2.0 AVAILABLE
<name1> <version1> <host1> <port1>
Security: <mechanism1>,<mechanism2>,...
<name2> <version2> <host2> <port2>
Security: <mechanism1>,<mechanism2>,...
```

Example:

```text
UTNP/2.0 AVAILABLE
tmutp 2.0 example.com 100
Security: tls,ssh
tbip 2.0 example.com 81
Security: tls
```

The server may return an empty list when no protocols are available:

```text
UTNP/2.0 AVAILABLE
```

### 2.4. EXPLORE Response

`EXPLORE` returns UTNP nodes known to or recommended by the responding server. This command reports node information; it does not negotiate a content-transfer protocol.

The response format is:

```text
UTNP/2.0 EXPLORE AVAILABLE
utnp <version> <host> <description>
...
```

Example:

```text
UTNP/2.0 EXPLORE AVAILABLE
utnp 2.0 example.com Our Second Site
```

Each node entry contains:

1. `utnp` — the protocol identifier. This value is always `utnp` for entries in an EXPLORE response.
2. The UTNP version advertised for that node.
3. The node host or address. A port is not included because UTNP uses the default port `34`.
4. A human-readable description extending to the end of the line.

The list may be empty:

```text
UTNP/2.0 EXPLORE AVAILABLE
```

The server controls which nodes it includes and the order in which they are returned.

### 2.5. Error Responses

General errors use:

```text
UTNP/2.0 ERROR <message>
```

If the requested protocol is not available, the server returns the error followed by the available-protocol list:

```text
UTNP/2.0 ERROR Unsupported protocol
UTNP/2.0 AVAILABLE
<name1> <version1> <host1> <port1>
Security: <mechanism1>,<mechanism2>,...
...
```

If the UTNP connection itself must be protected, the server returns:

```text
UTNP/2.0 ERROR REQUIRE SECURE
```

If none of the client's `Supported-Versions` are available for the requested protocol, the server returns an unsupported-version error:

```text
UTNP/2.0 ERROR Unsupported protocol version
```

If the UTNP version used by the client is not supported, the server returns a version error. For a server that supports UTNP/2.0, the response is:

```text
UTNP ERROR - UNSUPPORTED UTNP VERSION, SUPPORTED UTNP/2.0
```

### 2.6. Server Behavior

1. Listen on the UTNP port, `34` by default.
2. Accept a TCP connection and determine whether it begins with a supported TLS handshake, SSH handshake, or an unencrypted UTNP request.
3. Apply the server's connection-security policy. If protection is required and the request is unencrypted, return `UTNP/2.0 ERROR REQUIRE SECURE` when a textual response can be sent, then close the connection.
4. Read one UTNP request.
5. For `NEGOTIATE`, check the requested protocol and select a version compatible with `Supported-Versions`.
6. For `LIST`, return the available protocols and the `Security` information associated with each entry.
7. For `EXPLORE`, return the UTNP nodes known to or recommended by the server.
8. For an unsupported protocol, return `ERROR Unsupported protocol` followed by `AVAILABLE`.
9. Close the connection after sending the response.

### 2.7. Standard TNet Protocols

| Name | Version | Default port |
|------|---------|--------------|
| `tmutp` | `2.0` | `100` |
| `tbip` | `2.0` | `81` |

## 3. TMUTP — TMkUp Transfer Protocol

**Version:** `2.0`  
**Default port:** `100`  
**Transport:** TCP  
**Purpose:** Transfer TMkUp documents and text content.

### 3.1. Request Format

TMUTP/2.0 supports `GET` and `POST` requests.

**GET:**

```text
TMUTP/2.0 GET <path>
[Accept-Compression: <algorithm1>,<algorithm2>,...]
[Range: bytes=<start>-<end>]

```

**POST:**

```text
TMUTP/2.0 POST <path>
Content-Length: <length>
[Accept-Compression: <algorithm1>,<algorithm2>,...]

<request body>
```

Examples:

```text
TMUTP/2.0 GET /index.tmkup

```

```text
TMUTP/2.0 GET /docs/
Accept-Compression: <algorithm1>,<algorithm2>,...

```

```text
TMUTP/2.0 GET /article.tmkup
Range: bytes=100-500

```

```text
TMUTP/2.0 POST /feedback
Content-Length: 25

name=John&message=Hello
```

For `POST`, the request body format is `application/x-www-form-urlencoded` unless the server and application define another supported format.

### 3.2. Range Requests

TMUTP supports byte-range requests through the `Range` header:

```text
Range: bytes=<start>-<end>
```

The start and end positions are byte offsets in the source document. Both positions are inclusive. For example:

```text
Range: bytes=100-500
```

A successful response to a range request includes `Content-Range` in the response header section:

```text
Content-Range: bytes 100-500/<source-length>
```

The requested range is interpreted against the original source document, before response compression. If compression is used, `Content-Range` still identifies the byte positions in the original source document.

When a range request cannot be fulfilled, the server returns a complete error response and a complete error-page body. It must not return a truncated fragment of the error page. The response headers identify the requested range, the reason it is unavailable, and the size of the original source document:

```text
TMUTP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/tmkup
Content-Length: <error-page-length>
SOURCE-CONTENT-LENGTH: <original-source-length>
Range-Error: <requested-range>; <reason>

<complete TMkUp error page>
```

`SOURCE-CONTENT-LENGTH` is the size, in bytes, of the original source document. It is not the length of the error page or the transmitted response body.

The range-related status codes are:

- `52 INVALID RANGE` — the Range value is malformed or invalid.
- `53 RANGE NOT SATISFIABLE` — the requested byte range is outside the available source content or otherwise cannot be satisfied.
- `54 UNSUPPORTED RANGE` — the requested range unit or form is not supported.

For a range-related error, the response body is the complete TMkUp error page. The headers describe the range failure; the server does not place an error fragment in the document body.

### 3.3. Response Format

```text
TMUTP/2.0 <code> <name>
Content-Type: text/tmkup
Content-Length: <length>
[Content-Encoding: <algorithm>]
[Supported-Compression: <algorithm1>,<algorithm2>,...]
[Content-Range: bytes <start>-<end>/<source-length>]
[FILE-SHA256: <sha256>]
[SOURCE-CONTENT-LENGTH: <original-source-length>]
[Last-Modified: <date>]
[Location: <new-path>]
[Range-Error: <requested-range>; <reason>]

<TMkUp body>
```

All response headers, including `FILE-SHA256` and `SOURCE-CONTENT-LENGTH`, must appear before the empty line that begins the body.

`FILE-SHA256` contains the SHA-256 digest of the complete original source file, represented as hexadecimal text. It is metadata about the source file, not a trailer and not part of the body.

`SOURCE-CONTENT-LENGTH` contains the size in bytes of the complete original source file. When present on a range response, it describes the source file before range selection and before compression.

`Content-Length` describes the response body actually transmitted. If the body is compressed, this is the compressed body length.

### 3.4. Response Examples

**Successful response:**

```text
TMUTP/2.0 20 OK
Content-Type: text/tmkup
Content-Length: 100
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 100
Last-Modified: 2024-06-10

---tmk-meta
title: "Home"
---tmk-meta
# Welcome!
```

**Successful range response:**

```text
TMUTP/2.0 20 OK
Content-Type: text/tmkup
Content-Length: <range-body-length>
Content-Range: bytes 100-500/1000
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 1000

<requested source bytes>
```

**Range error response:**

```text
TMUTP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/tmkup
Content-Length: <error-page-length>
SOURCE-CONTENT-LENGTH: 1000
Range-Error: bytes=1200-1500; outside-source

---tmk-meta
title: "53 — Range Not Satisfiable"
---tmk-meta
# The requested range is not available.
```

**Moved resource:**

```text
TMUTP/2.0 21 MOVED
Content-Type: text/tmkup
Content-Length: 0
Location: /index.tmkup
```

**Secure connection required:**

```text
TMUTP/2.0 55 REQUIRE SECURE
Content-Type: text/tmkup
Content-Length: <error-page-length>

<complete TMkUp error page>
```

### 3.5. Headers

**Request headers:**

| Header | Description | Example |
|--------|-------------|---------|
| `Content-Length` | Request-body length in bytes, used by `POST` | `Content-Length: 25` |
| `Accept-Compression` | Compression algorithms the client can decode | `Accept-Compression: <algorithm1>,<algorithm2>` |
| `Range` | Requested byte range of the source document | `Range: bytes=100-500` |

**Response headers:**

| Header | Description | Example |
|--------|-------------|---------|
| `Content-Type` | TMkUp content type | `Content-Type: text/tmkup` |
| `Content-Length` | Number of bytes in the transmitted response body | `Content-Length: 1024` |
| `Content-Encoding` | Compression algorithm actually used, when applicable | `Content-Encoding: <algorithm>` |
| `Supported-Compression` | Compression algorithms supported by the server | `Supported-Compression: <algorithm1>,<algorithm2>` |
| `Content-Range` | Byte interval returned and total source length | `Content-Range: bytes 100-500/1000` |
| `FILE-SHA256` | SHA-256 digest of the complete original source file | `FILE-SHA256: <sha256>` |
| `SOURCE-CONTENT-LENGTH` | Size in bytes of the complete original source file | `SOURCE-CONTENT-LENGTH: 1000` |
| `Last-Modified` | Last modification date of the source document | `Last-Modified: 2024-06-10` |
| `Location` | New path for a `21 MOVED` response | `Location: /index.tmkup` |
| `Range-Error` | Requested range and reason it could not be fulfilled | `Range-Error: bytes=1200-1500; outside-source` |

### 3.6. Server Behavior

1. Accept a TCP connection on port `100` by default.
2. Determine whether the connection uses TLS, SSH, or an unencrypted request, then apply the server's security policy.
3. If a protected connection is required and the request is unencrypted, return `55 REQUIRE SECURE` and close the connection.
4. Read the request line and all request headers.
5. Check the TMUTP version. If the version is unsupported, return `51 VERSION NOT SUPPORTED`.
6. If the request is `GET`:
   - If the path ends with `/`, look for `index.tmkup` in the directory.
   - Otherwise, look for a file exactly by name; do not append an extension.
   - If the resource exists, return `20 OK` with the TMkUp content and applicable metadata.
   - If a valid `Range` is present, return the requested range and `Content-Range` metadata.
   - If the resource does not exist, return `31 NOT FOUND` with a complete TMkUp error page.
   - If the path contains parameters, such as `/search?q=...`, the server handles them according to its application.
7. If the request is `POST`:
   - Read exactly `Content-Length` bytes.
   - Process the request body.
   - Return `20 OK` with a response body or `22 OK EMPTY`.
8. Negotiate response compression using `Accept-Compression` and the server's supported algorithms. If no mutually supported algorithm is available, send the response without compression.
9. If the method is neither `GET` nor `POST`, return `50 METHOD NOT ALLOWED`.
10. If the request body format is unsupported, return `41 NOT IMPLEMENTED`.

## 4. TBIP — TNet Binary Information Protocol

**Version:** `2.0`  
**Default port:** `81`  
**Transport:** TCP  
**Purpose:** Transfer binary information such as images, audio, and video. Executable files, including `.exe` and `.bin` files, are not considered binary information for the purposes of TBIP.

### 4.1. Request Format

TBIP/2.0 supports `GET` and `HEAD` requests.

**GET:**

```text
TBIP/2.0 GET <path>
[Accept-Compression: <algorithm1>,<algorithm2>,...]
[Range: bytes=<start>-<end>]

```

**HEAD:**

```text
TBIP/2.0 HEAD <path>
[Accept-Compression: <algorithm1>,<algorithm2>,...]

```

Examples:

```text
TBIP/2.0 GET /logo.png

```

```text
TBIP/2.0 GET /video/clip.mp4
Range: bytes=100-500

```

```text
TBIP/2.0 HEAD /audio/song.mp3

```

### 4.2. Range Requests

TBIP supports a single byte range per request. The `Range` header has the following form:

```text
Range: bytes=<start>-<end>
```

The start and end positions are byte offsets in the original source file. Both positions are inclusive. A request containing more than one range is not supported and is rejected with `54 UNSUPPORTED RANGE`.

For a successful range response, the server includes:

```text
Content-Range: bytes <start>-<end>/<source-length>
```

The range is selected from the original source file before response compression. `Content-Range` and `SOURCE-CONTENT-LENGTH` therefore refer to the original file, not to the compressed response body.

When a range request cannot be fulfilled, the server returns a complete error response with a complete error body. It must not return a partial fragment of the error body. The response headers identify the requested range, the reason it is unavailable, and the original source length when the source file exists:

```text
TBIP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/plain
Content-Length: <error-body-length>
SOURCE-CONTENT-LENGTH: <original-source-length>
Range-Error: <requested-range>; <reason>

<complete error body>
```

The range-related status codes are `52 INVALID RANGE`, `53 RANGE NOT SATISFIABLE`, and `54 UNSUPPORTED RANGE`, as defined in the common TNet Status Codes table.

### 4.3. Response Format

```text
TBIP/2.0 <code> <name>
Content-Type: <type>
Content-Length: <length>
[Content-Encoding: <algorithm>]
[Supported-Compression: <algorithm1>,<algorithm2>,...]
[Content-Range: bytes <start>-<end>/<source-length>]
[FILE-SHA256: <sha256>]
[SOURCE-CONTENT-LENGTH: <original-source-length>]
[Last-Modified: <date>]
[Location: <new-path>]
[Range-Error: <requested-range>; <reason>]

<binary data or complete error body>
```

All headers, including `FILE-SHA256` and `SOURCE-CONTENT-LENGTH`, must appear before the empty line that begins the body.

`FILE-SHA256` contains the SHA-256 digest of the complete original source file, represented as hexadecimal text. It is a response header, not a trailer.

`SOURCE-CONTENT-LENGTH` contains the size in bytes of the complete original source file, before range selection and before compression.

`Content-Length` contains the number of bytes actually transmitted in the response body. If compression is used, this is the compressed body length.

### 4.4. Content Types

The server determines the content type from the file type, using the file extension or file contents where appropriate.

| Content type | Description |
|--------------|-------------|
| `image/png` | PNG image |
| `image/jpeg` | JPEG image |
| `image/gif` | GIF image |
| `image/webp` | WebP image |
| `audio/mpeg` | MP3 audio |
| `audio/ogg` | OGG audio |
| `video/mp4` | MP4 video |
| `video/webm` | WebM video |
| `application/octet-stream` | Other binary data; the client may offer to save it |
| `text/plain` | Plain-text error body |

### 4.5. Response Examples

**Successful response:**

```text
TBIP/2.0 20 OK
Content-Type: image/png
Content-Length: 12345
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 12345
Last-Modified: 2024-06-12

<binary PNG data>
```

**Successful range response:**

```text
TBIP/2.0 20 OK
Content-Type: video/mp4
Content-Length: <range-body-length>
Content-Range: bytes 100-500/12345
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 12345

<requested binary bytes>
```

**Unsupported multiple ranges:**

```text
TBIP/2.0 54 UNSUPPORTED RANGE
Content-Type: text/plain
Content-Length: <error-body-length>
SOURCE-CONTENT-LENGTH: 12345
Range-Error: bytes=0-100,200-300; multiple-ranges-not-supported

The requested range form is not supported.
```

**Secure connection required:**

```text
TBIP/2.0 55 REQUIRE SECURE
Content-Type: text/plain
Content-Length: <error-body-length>

A secure connection is required.
```

### 4.6. Headers

**Request headers:**

| Header | Description | Example |
|--------|-------------|---------|
| `Accept-Compression` | Compression algorithms the client can decode | `Accept-Compression: <algorithm1>,<algorithm2>` |
| `Range` | A single requested byte range | `Range: bytes=100-500` |

**Response headers:**

| Header | Description | Example |
|--------|-------------|---------|
| `Content-Type` | MIME type of the returned data | `Content-Type: image/png` |
| `Content-Length` | Number of bytes in the transmitted body | `Content-Length: 12345` |
| `Content-Encoding` | Compression algorithm actually used, when applicable | `Content-Encoding: <algorithm>` |
| `Supported-Compression` | Compression algorithms supported by the server | `Supported-Compression: <algorithm1>,<algorithm2>` |
| `Content-Range` | Returned byte interval and total source length | `Content-Range: bytes 100-500/12345` |
| `FILE-SHA256` | SHA-256 digest of the complete original source file | `FILE-SHA256: <sha256>` |
| `SOURCE-CONTENT-LENGTH` | Size in bytes of the complete original source file | `SOURCE-CONTENT-LENGTH: 12345` |
| `Last-Modified` | Last modification date of the source file | `Last-Modified: 2024-06-12` |
| `Location` | New path for a `21 MOVED` response | `Location: /media/new-logo.png` |
| `Range-Error` | Requested range and reason it could not be fulfilled | `Range-Error: bytes=20000-21000; outside-source` |

### 4.7. Server Behavior

1. Accept a TCP connection on port `81` by default.
2. Determine whether the connection uses TLS, SSH, or an unencrypted request, then apply the server's security policy.
3. If a protected connection is required and the request is unencrypted, return `55 REQUIRE SECURE` and close the connection.
4. Read the request line and headers.
5. Check the TBIP version. If the version is unsupported, return `51 VERSION NOT SUPPORTED`.
6. If the method is `GET` or `HEAD`:
   - Look for a file exactly by name; do not append an extension.
   - If the resource exists, determine its content type and return the appropriate metadata.
   - For `GET`, send the resource body. For `HEAD`, send the response headers without a body.
   - If a single valid `Range` is present on a `GET` request, return the requested bytes and `Content-Range` metadata.
   - Reject a request containing multiple ranges with `54 UNSUPPORTED RANGE`.
   - If the resource does not exist, return `31 NOT FOUND`.
   - If the path is a directory, return `31 NOT FOUND`; TBIP does not resolve a directory to an index file by default.
7. Negotiate response compression using `Accept-Compression` and the server's supported algorithms. If no mutually supported algorithm is available, send the response without compression.
8. If the method is neither `GET` nor `HEAD`, return `50 METHOD NOT ALLOWED`.

`Content-Length` always describes the transmitted response body. Chunked transfer is not used. The client reads exactly `Content-Length` bytes.

## 5. TNet Workflow

A client first uses UTNP to discover the endpoint and version of the required content protocol. It then opens a separate TCP connection to that protocol's advertised host and port.

Example workflow for retrieving a TMkUp document:

```text
Client connects to the UTNP endpoint on port 34
  |
  |-- UTNP/2.0 NEGOTIATE tmutp
  |   Supported-Versions: 1.0,2.0
  |
  |<-- UTNP/2.0 START PROTOCOL tmutp 2.0 example.com 100
  |    Security: tls,ssh
  |
  |-- closes the UTNP connection
  |
  |-- connects to example.com:100 using a transport accepted by the server
  |-- TMUTP/2.0 GET /index.tmkup
  |   Accept-Compression: <algorithm1>,<algorithm2>
  |
  |<-- TMUTP/2.0 20 OK + TMkUp document
```

If the document refers to a binary resource, the client negotiates TBIP separately:

```text
Client connects to the UTNP endpoint on port 34
  |
  |-- UTNP/2.0 NEGOTIATE tbip
  |   Supported-Versions: 1.0,2.0
  |
  |<-- UTNP/2.0 START PROTOCOL tbip 2.0 example.com 81
  |    Security: tls
  |
  |-- closes the UTNP connection
  |
  |-- connects to example.com:81 using a transport accepted by the server
  |-- TBIP/2.0 GET /logo.png
  |   Accept-Compression: <algorithm1>,<algorithm2>
  |
  |<-- TBIP/2.0 20 OK + binary image data
```

A client must apply its own security policy when choosing TLS, SSH, or unencrypted transport. The `Security` value received through UTNP is informational and does not replace the transport handshake.

## 6. Version 2.0 Summary

The main additions and changes in TNet Protocols 2.0 are:

- UTNP supports single-protocol negotiation with `Supported-Versions` version negotiation.
- UTNP `START PROTOCOL` and `AVAILABLE` entries include a `Security` list.
- UTNP adds `EXPLORE` to return known or recommended UTNP nodes.
- UTNP, TMUTP, and TBIP can operate over TLS, SSH, or unencrypted TCP on the same protocol port, subject to client and server policy.
- TMUTP and TBIP support compression negotiation through request and response headers.
- TMUTP and TBIP include source-file metadata headers such as `FILE-SHA256` and `SOURCE-CONTENT-LENGTH`.
- TMUTP and TBIP support byte-range requests and define range-related status codes `52`, `53`, and `54`.
- Status code `55` is `REQUIRE SECURE`.
