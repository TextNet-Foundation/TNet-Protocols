# Спецификация протоколов TNet — версия 2.0

Этот документ описывает три основных протокола **TNet**, децентрализованной текстовой сети:

- **UTNP** — Universal Text Negotiation Protocol;
- **TMUTP** — TMkUp Transfer Protocol;
- **TBIP** — TNet Binary Information Protocol.

Все три протокола работают поверх TCP. UTNP используется для обнаружения служб, согласования протоколов и поиска других узлов UTNP. TMUTP передаёт документы TMkUp, а TBIP — бинарные ресурсы.

---

## 1. Общие правила протоколов

### 1.1. Версии протоколов

Версия протокола указывается в первой строке каждого запроса и ответа:

```text
UTNP/2.0
TMUTP/2.0
TBIP/2.0
```

Версия определяет версию протокола, используемую в данном соединении. Версия протокола, выбранная через UTNP, согласуется отдельно от версии самого UTNP.

### 1.2. Транспорт

Протоколы используют TCP. Порты по умолчанию:

| Протокол | Порт по умолчанию |
|----------|-------------------|
| `utnp`   | `34`              |
| `tmutp`  | `100`             |
| `tbip`   | `81`              |

Сервер может использовать другой порт и сообщить его через UTNP.

### 1.3. Кодировка текста и структура сообщений

Строки команд и заголовки являются текстовыми. Для текстовых значений реализации должны использовать UTF-8. Имена заголовков регистронезависимы. Значения заголовков интерпретируются согласно определению соответствующего заголовка.

Запрос или ответ состоит из стартовой строки, нуля или нескольких строк заголовков, пустой строки-разделителя между заголовками и телом, а также необязательного тела:

```text
<стартовая строка протокола>
<Имя-Заголовка>: <значение>
<Другой-Заголовок>: <значение>

<тело>
```

Все заголовки должны находиться в секции заголовков — до пустой строки. Метаданные протокола нельзя добавлять после тела.

`Content-Length` измеряется в байтах, а не в символах. Если ответ содержит тело, получатель считывает ровно столько байтов, сколько указано в `Content-Length`.

### 1.4. Коды состояния TNet

TMUTP и TBIP используют общую таблицу **кодов состояния TNet**. Код имеет одинаковое значение в обоих протоколах, если раздел конкретного протокола явно не ограничивает его применение.

| Код | Название | Описание |
|-----|----------|----------|
| `20` | `OK` | Успешный ответ с содержимым или данными |
| `21` | `MOVED` | Запрошенный ресурс перемещён |
| `22` | `OK EMPTY` | Успешный ответ с пустым телом |
| `23` | `MULTIPLE CHOICES` | Доступно несколько вариантов |
| `30` | `BAD REQUEST` | Запрос некорректен или имеет неверный формат |
| `31` | `NOT FOUND` | Запрошенный документ или ресурс не найден |
| `32` | `FORBIDDEN` | Доступ к запрошенному ресурсу запрещён |
| `40` | `SERVER ERROR` | Произошла внутренняя ошибка сервера |
| `41` | `NOT IMPLEMENTED` | Запрошенный метод или функциональность не реализованы |
| `42` | `SERVICE UNAVAILABLE` | Служба временно недоступна |
| `50` | `METHOD NOT ALLOWED` | Запрошенный метод не разрешён |
| `51` | `VERSION NOT SUPPORTED` | Запрошенная версия протокола не поддерживается |
| `52` | `INVALID RANGE` | Заголовок `Range` имеет некорректное значение |
| `53` | `RANGE NOT SATISFIABLE` | Запрошенный диапазон не может быть предоставлен из исходного ресурса |
| `54` | `UNSUPPORTED RANGE` | Запрошенная форма диапазона или единица диапазона не поддерживается |
| `55` | `REQUIRE SECURE` | Сервер требует защищённое соединение |

UTNP использует собственные текстовые ответы об ошибках вместо числовых кодов состояния TNet.

### 1.5. Защищённые соединения

UTNP, TMUTP и TBIP могут работать через защищённое или незащищённое TCP-соединение. Сервер может принимать любые поддерживаемые варианты из следующих:

- TLS handshake;
- SSH handshake;
- незашифрованный запрос протокола.

Все эти варианты используют один и тот же TCP-порт соответствующего протокола. Сервер не должен требовать отдельный порт только потому, что клиент использует TLS или SSH. Тип соединения определяется сервером по начальному handshake или данным протокола.

Клиент и сервер применяют собственные политики безопасности. Клиенту рекомендуется отдавать предпочтение защищённому соединению. Сервер может требовать защищённое соединение и отклонять незашифрованные запросы.

UTNP сообщает о поддерживаемых защищённых способах соединения с помощью заголовка `Security`. Его значение представляет собой список, разделённый запятыми:

```text
Security: tls,ssh
```

Этот заголовок носит информационный характер: он сообщает о механизмах защиты, связанных с объявленной службой, но сам по себе не выбирает механизм и не заменяет handshake. Клиент выбирает способ соединения согласно собственной политике, а сервер принимает или отклоняет фактический handshake согласно своим возможностям и политике. Клиент может попытаться использовать механизм, даже если он не указан в `Security`; успешное установление соединения зависит от того, принимает ли его сервер.

`Security` перечисляет только защищённые механизмы. Незашифрованный режим не обозначается значением `none`.

Если сервер требует защищённое соединение:

- UTNP возвращает `UTNP/2.0 ERROR REQUIRE SECURE`, если сам запрос UTNP не был защищён;
- TMUTP или TBIP возвращает код `55 REQUIRE SECURE`, если запрос не был защищён.

Клиент не должен незаметно переходить на незашифрованное соединение, если его собственная политика безопасности запрещает это.

## 2. UTNP — Universal Text Negotiation Protocol

**Версия:** `2.0`  
**Порт по умолчанию:** `34`  
**Транспорт:** TCP  
**Назначение:** обнаружение служб, согласование версий протоколов и обнаружение других узлов UTNP. UTNP не передаёт документы или бинарное содержимое и не используется в качестве схемы URL для содержимого.

### 2.1. Запросы

UTNP/2.0 определяет три команды:

```text
UTNP/2.0 NEGOTIATE <protocol>
UTNP/2.0 LIST
UTNP/2.0 EXPLORE
```

`NEGOTIATE` запрашивает ровно один протокол. Запрос не должен содержать список имён протоколов, разделённых запятыми.

Для `NEGOTIATE` клиент передаёт версии запрашиваемого протокола, которые он поддерживает:

```text
UTNP/2.0 NEGOTIATE tmutp
Supported-Versions: 1.0,2.0
```

`Supported-Versions` — список версий, поддерживаемых клиентом для запрашиваемого протокола, разделённый запятыми.

`LIST` запрашивает список протоколов, доступных на сервере:

```text
UTNP/2.0 LIST
```

`EXPLORE` запрашивает список узлов UTNP, известных серверу или рекомендованных им:

```text
UTNP/2.0 EXPLORE
```

### 2.2. Успешный ответ на согласование

Если запрошенный протокол доступен и найдена совместимая версия, сервер отвечает:

```text
UTNP/2.0 START PROTOCOL <name> <version> <host> <port>
Security: <mechanism1>,<mechanism2>,...
```

Пример:

```text
UTNP/2.0 START PROTOCOL tmutp 2.0 example.com 100
Security: tls,ssh
```

Ответ содержит:

- выбранное имя протокола;
- выбранную версию протокола;
- хост, на котором доступен протокол;
- TCP-порт, на котором доступен протокол;
- объявленные для этой службы защищённые способы соединения через `Security`.

Сервер выбирает версию протокола, поддерживаемую и клиентом, и сервером. Если совместимы несколько версий, сервер выбирает самую высокую из них. Порядок версий в `Supported-Versions` не влияет на это правило.

`Security` является списком, а не одним выбранным способом соединения. Клиент не обязан считать первый элемент единственным допустимым вариантом.

### 2.3. Ответ на запрос списка протоколов

На команду `LIST` сервер отвечает `AVAILABLE`. Каждая запись протокола содержит его имя, версию, хост и порт. Следующий непосредственно за записью заголовок `Security` описывает объявленные защищённые способы соединения для этой записи.

```text
UTNP/2.0 AVAILABLE
<name1> <version1> <host1> <port1>
Security: <mechanism1>,<mechanism2>,...
<name2> <version2> <host2> <port2>
Security: <mechanism1>,<mechanism2>,...
```

Пример:

```text
UTNP/2.0 AVAILABLE
tmutp 2.0 example.com 100
Security: tls,ssh
tbip 2.0 example.com 81
Security: tls
```

Если доступных протоколов нет, сервер может вернуть пустой список:

```text
UTNP/2.0 AVAILABLE
```

### 2.4. Ответ на EXPLORE

`EXPLORE` возвращает узлы UTNP, известные серверу или рекомендованные им. Эта команда сообщает информацию об узлах и не согласует протокол передачи содержимого.

Формат ответа:

```text
UTNP/2.0 EXPLORE AVAILABLE
utnp <version> <host> <description>
...
```

Пример:

```text
UTNP/2.0 EXPLORE AVAILABLE
utnp 2.0 example.com Our Second Site
```

Каждая запись узла содержит:

1. `utnp` — идентификатор протокола. В записях ответа `EXPLORE` это значение всегда равно `utnp`.
2. Версию UTNP, объявленную этим узлом.
3. Хост или адрес узла. Порт не указывается, поскольку UTNP использует порт `34` по умолчанию.
4. Человекочитаемое описание, занимающее остаток строки.

Список может быть пустым:

```text
UTNP/2.0 EXPLORE AVAILABLE
```

Сервер самостоятельно определяет, какие узлы включать в ответ и в каком порядке их возвращать.

### 2.5. Ответы об ошибках

Общие ошибки возвращаются в следующем формате:

```text
UTNP/2.0 ERROR <message>
```

Если запрошенный протокол недоступен, сервер возвращает ошибку, за которой следует список доступных протоколов:

```text
UTNP/2.0 ERROR Unsupported protocol
UTNP/2.0 AVAILABLE
<name1> <version1> <host1> <port1>
Security: <mechanism1>,<mechanism2>,...
...
```

Если само соединение UTNP должно быть защищено, сервер возвращает:

```text
UTNP/2.0 ERROR REQUIRE SECURE
```

Если ни одна из версий `Supported-Versions` клиента не доступна для запрошенного протокола, сервер возвращает ошибку неподдерживаемой версии протокола:

```text
UTNP/2.0 ERROR Unsupported protocol version
```

Если версия UTNP, используемая клиентом, не поддерживается, сервер возвращает ошибку версии. Для сервера, поддерживающего UTNP/2.0, ответ имеет вид:

```text
UTNP ERROR - UNSUPPORTED UTNP VERSION, SUPPORTED UTNP/2.0
```

### 2.6. Поведение сервера

1. Ожидать соединения на порту UTNP — `34` по умолчанию.
2. Принять TCP-соединение и определить, начинается ли оно с поддерживаемого TLS handshake, SSH handshake или незашифрованного запроса UTNP.
3. Применить политику безопасности соединений сервера. Если защита обязательна, а запрос не зашифрован, вернуть `UTNP/2.0 ERROR REQUIRE SECURE`, если возможно отправить текстовый ответ, а затем закрыть соединение.
4. Прочитать один запрос UTNP.
5. Для `NEGOTIATE` проверить запрошенный протокол и выбрать версию, совместимую с `Supported-Versions`.
6. Для `LIST` вернуть доступные протоколы и сведения `Security`, относящиеся к каждой записи.
7. Для `EXPLORE` вернуть узлы UTNP, известные серверу или рекомендованные им.
8. Для неподдерживаемого протокола вернуть `ERROR Unsupported protocol`, а затем `AVAILABLE`.
9. Закрыть соединение после отправки ответа.

### 2.7. Стандартные протоколы TNet

| Имя | Версия | Порт по умолчанию |
|-----|--------|-------------------|
| `tmutp` | `2.0` | `100` |
| `tbip` | `2.0` | `81` |

## 3. TMUTP — TMkUp Transfer Protocol

**Версия:** `2.0`  
**Порт по умолчанию:** `100`  
**Транспорт:** TCP  
**Назначение:** передача документов TMkUp и текстового содержимого.

### 3.1. Формат запроса

TMUTP/2.0 поддерживает запросы `GET` и `POST`.

**GET:**

```text
TMUTP/2.0 GET <path>
[Range: bytes=<start>-<end>]

```

**POST:**

```text
TMUTP/2.0 POST <path>
Content-Length: <length>

<тело запроса>
```

Примеры:

```text
TMUTP/2.0 GET /index.tmkup

```

```text
TMUTP/2.0 GET /article.tmkup
Range: bytes=100-500

```

```text
TMUTP/2.0 POST /feedback
Content-Length: 25

name=John&message=Hello
```

Для `POST` формат тела запроса — `application/x-www-form-urlencoded`, если сервер и приложение не определяют другой поддерживаемый формат.

### 3.2. Запросы диапазонов

TMUTP поддерживает запросы диапазонов байтов с помощью заголовка `Range`:

```text
Range: bytes=<start>-<end>
```

Начальная и конечная позиции — смещения в байтах исходного документа. Обе позиции включаются в диапазон. Например:

```text
Range: bytes=100-500
```

Успешный ответ на запрос диапазона содержит `Content-Range` в секции заголовков ответа:

```text
Content-Range: bytes 100-500/<source-length>
```

Запрошенный диапазон определяется относительно исходного документа до возможного сжатия ответа. Если используется сжатие, `Content-Range` всё равно указывает позиции байтов в исходном документе.

Если запрос диапазона не может быть выполнен, сервер возвращает полный ответ об ошибке и полное тело страницы ошибки. Он не должен возвращать усечённый фрагмент страницы ошибки. Заголовки ответа указывают, какая часть недоступна, причину недоступности и размер исходного файла:

```text
TMUTP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/tmkup
Content-Length: <error-page-length>
SOURCE-CONTENT-LENGTH: <original-source-length>
Range-Error: <requested-range>; <reason>

<полная страница ошибки TMkUp>
```

`SOURCE-CONTENT-LENGTH` — размер исходного документа в байтах. Это не длина страницы ошибки и не длина передаваемого тела ответа.

Коды состояния, связанные с диапазонами:

- `52 INVALID RANGE` — значение `Range` некорректно.
- `53 RANGE NOT SATISFIABLE` — запрошенный диапазон выходит за пределы доступного содержимого источника или по другой причине не может быть предоставлен.
- `54 UNSUPPORTED RANGE` — запрошенная единица или форма диапазона не поддерживается.

При ошибке диапазона тело ответа представляет собой полную страницу ошибки TMkUp. Заголовки описывают причину ошибки диапазона; сервер не помещает фрагмент ошибки в тело документа.

### 3.3. Формат ответа

```text
TMUTP/2.0 <code> <name>
Content-Type: text/tmkup
Content-Length: <length>
[Content-Range: bytes <start>-<end>/<source-length>]
[FILE-SHA256: <sha256>]
[SOURCE-CONTENT-LENGTH: <original-source-length>]
[Last-Modified: <date>]
[Location: <new-path>]
[Range-Error: <requested-range>; <reason>]

<тело TMkUp>
```

Все заголовки ответа, включая `FILE-SHA256` и `SOURCE-CONTENT-LENGTH`, должны располагаться до пустой строки, начинающей тело.

`FILE-SHA256` содержит SHA-256 хеш полного исходного файла в шестнадцатеричном представлении. Это метаданные исходного файла, а не завершающая часть сообщения и не часть тела.

`SOURCE-CONTENT-LENGTH` содержит размер полного исходного файла в байтах. В ответе на запрос диапазона он описывает исходный файл до выбора диапазона.

`Content-Length` описывает фактически передаваемое тело ответа.

### 3.4. Примеры ответов

**Успешный ответ:**

```text
TMUTP/2.0 20 OK
Content-Type: text/tmkup
Content-Length: 100
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 100
Last-Modified: 2024-06-10

---tmk-meta
title: "Home"
---tmk-meta
# Welcome!
```

**Успешный ответ на запрос диапазона:**

```text
TMUTP/2.0 20 OK
Content-Type: text/tmkup
Content-Length: <range-body-length>
Content-Range: bytes 100-500/1000
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 1000

<запрошенные байты исходного документа>
```

**Ответ об ошибке диапазона:**

```text
TMUTP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/tmkup
Content-Length: <error-page-length>
SOURCE-CONTENT-LENGTH: 1000
Range-Error: bytes=1200-1500; outside-source

---tmk-meta
title: "53 — Range Not Satisfiable"
---tmk-meta
# The requested range is not available.
```

**Перемещённый ресурс:**

```text
TMUTP/2.0 21 MOVED
Content-Type: text/tmkup
Content-Length: 0
Location: /index.tmkup
```

**Требуется защищённое соединение:**

```text
TMUTP/2.0 55 REQUIRE SECURE
Content-Type: text/tmkup
Content-Length: <error-page-length>

<полная страница ошибки TMkUp>
```

### 3.5. Заголовки

**Заголовки запроса:**

| Заголовок | Описание | Пример |
|-----------|----------|--------|
| `Content-Length` | Длина тела запроса в байтах; используется в `POST` | `Content-Length: 25` |
| `Range` | Запрашиваемый диапазон байтов исходного документа | `Range: bytes=100-500` |

**Заголовки ответа:**

| Заголовок | Описание | Пример |
|-----------|----------|--------|
| `Content-Type` | Тип содержимого TMkUp | `Content-Type: text/tmkup` |
| `Content-Length` | Количество байтов в передаваемом теле ответа | `Content-Length: 1024` |
| `Content-Range` | Возвращённый интервал байтов и полный размер источника | `Content-Range: bytes 100-500/1000` |
| `FILE-SHA256` | SHA-256 хеш полного исходного файла | `FILE-SHA256: <sha256>` |
| `SOURCE-CONTENT-LENGTH` | Размер полного исходного файла в байтах | `SOURCE-CONTENT-LENGTH: 1000` |
| `Last-Modified` | Дата последнего изменения исходного документа | `Last-Modified: 2024-06-10` |
| `Location` | Новый путь для ответа `21 MOVED` | `Location: /index.tmkup` |
| `Range-Error` | Запрошенный диапазон и причина, по которой он не может быть предоставлен | `Range-Error: bytes=1200-1500; outside-source` |

### 3.6. Поведение сервера

1. Принять TCP-соединение на порту `100` по умолчанию.
2. Определить, используется ли TLS, SSH или незашифрованный запрос, а затем применить политику безопасности сервера.
3. Если требуется защищённое соединение, а запрос не зашифрован, вернуть `55 REQUIRE SECURE` и закрыть соединение.
4. Прочитать строку запроса и все заголовки запроса.
5. Проверить версию TMUTP. Если версия не поддерживается, вернуть `51 VERSION NOT SUPPORTED`.
6. Если запрос — `GET`:
   - Если путь заканчивается на `/`, найти в каталоге `index.tmkup`.
   - В противном случае искать файл с точно указанным именем; не добавлять расширение автоматически.
   - Если ресурс существует, вернуть `20 OK` с содержимым TMkUp и соответствующими метаданными.
   - Если указан корректный `Range`, вернуть запрошенный диапазон и метаданные `Content-Range`.
   - Если ресурс не существует, вернуть `31 NOT FOUND` с полной страницей ошибки TMkUp.
   - Если путь содержит параметры, например `/search?q=...`, сервер обрабатывает их согласно логике приложения.
7. Если запрос — `POST`:
   - Считать ровно `Content-Length` байтов.
   - Обработать тело запроса.
   - Вернуть `20 OK` с телом ответа или `22 OK EMPTY`.
8. Если метод не `GET` и не `POST`, вернуть `50 METHOD NOT ALLOWED`.
9. Если формат тела запроса не поддерживается, вернуть `41 NOT IMPLEMENTED`.

## 4. TBIP — TNet Binary Information Protocol

**Версия:** `2.0`  
**Порт по умолчанию:** `81`  
**Транспорт:** TCP  
**Назначение:** передача бинарной информации, например изображений, аудио и видео. Исполняемые файлы, включая `.exe` и `.bin`, не считаются бинарной информацией в контексте TBIP.

### 4.1. Формат запроса

TBIP/2.0 поддерживает запросы `GET` и `HEAD`.

**GET:**

```text
TBIP/2.0 GET <path>
[Range: bytes=<start>-<end>]

```

**HEAD:**

```text
TBIP/2.0 HEAD <path>

```

Примеры:

```text
TBIP/2.0 GET /logo.png

```

```text
TBIP/2.0 GET /video/clip.mp4
Range: bytes=100-500

```

```text
TBIP/2.0 HEAD /audio/song.mp3

```

### 4.2. Запросы диапазонов

TBIP поддерживает один диапазон байтов на запрос. Заголовок `Range` имеет следующий формат:

```text
Range: bytes=<start>-<end>
```

Начальная и конечная позиции — смещения в байтах исходного файла. Обе позиции включаются в диапазон. Запрос, содержащий более одного диапазона, не поддерживается и отклоняется с кодом `54 UNSUPPORTED RANGE`.

Для успешного ответа на запрос диапазона сервер включает:

```text
Content-Range: bytes <start>-<end>/<source-length>
```

Диапазон выбирается из исходного файла до возможного сжатия ответа. Поэтому `Content-Range` и `SOURCE-CONTENT-LENGTH` относятся к исходному файлу, а не к передаваемому телу ответа.

Если запрос диапазона не может быть выполнен, сервер возвращает полный ответ об ошибке с полным телом ошибки. Он не должен возвращать частичный фрагмент тела ошибки. Заголовки ответа указывают запрошенный диапазон, причину его недоступности и исходный размер файла, если исходный файл существует:

```text
TBIP/2.0 53 RANGE NOT SATISFIABLE
Content-Type: text/plain
Content-Length: <error-body-length>
SOURCE-CONTENT-LENGTH: <original-source-length>
Range-Error: <requested-range>; <reason>

<полное тело ошибки>
```

Коды состояния, связанные с диапазонами: `52 INVALID RANGE`, `53 RANGE NOT SATISFIABLE` и `54 UNSUPPORTED RANGE`, как определено в общей таблице кодов состояния TNet.

### 4.3. Формат ответа

```text
TBIP/2.0 <code> <name>
Content-Type: <type>
Content-Length: <length>
[Content-Range: bytes <start>-<end>/<source-length>]
[FILE-SHA256: <sha256>]
[SOURCE-CONTENT-LENGTH: <original-source-length>]
[Last-Modified: <date>]
[Location: <new-path>]
[Range-Error: <requested-range>; <reason>]

<бинарные данные или полное тело ошибки>
```

Все заголовки, включая `FILE-SHA256` и `SOURCE-CONTENT-LENGTH`, должны находиться до пустой строки, начинающей тело.

`FILE-SHA256` содержит SHA-256 хеш полного исходного файла в шестнадцатеричном представлении. Это заголовок ответа, а не завершающая часть сообщения.

`SOURCE-CONTENT-LENGTH` содержит размер полного исходного файла в байтах до выбора диапазона.

`Content-Length` содержит количество байтов, фактически передаваемых в теле ответа.

### 4.4. Типы содержимого

Сервер определяет тип содержимого по типу файла, используя расширение или, если это уместно, само содержимое файла.

| Тип содержимого | Описание |
|-----------------|----------|
| `image/png` | Изображение PNG |
| `image/jpeg` | Изображение JPEG |
| `image/gif` | Изображение GIF |
| `image/webp` | Изображение WebP |
| `audio/mpeg` | Аудио MP3 |
| `audio/ogg` | Аудио OGG |
| `video/mp4` | Видео MP4 |
| `video/webm` | Видео WebM |
| `application/octet-stream` | Другие бинарные данные; клиент может предложить сохранить их |
| `text/plain` | Текстовое тело ошибки |

### 4.5. Примеры ответов

**Успешный ответ:**

```text
TBIP/2.0 20 OK
Content-Type: image/png
Content-Length: 12345
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 12345
Last-Modified: 2024-06-12

<бинарные данные PNG>
```

**Успешный ответ на запрос диапазона:**

```text
TBIP/2.0 20 OK
Content-Type: video/mp4
Content-Length: <range-body-length>
Content-Range: bytes 100-500/12345
FILE-SHA256: <sha256>
SOURCE-CONTENT-LENGTH: 12345

<запрошенные бинарные данные>
```

**Несколько диапазонов не поддерживаются:**

```text
TBIP/2.0 54 UNSUPPORTED RANGE
Content-Type: text/plain
Content-Length: <error-body-length>
SOURCE-CONTENT-LENGTH: 12345
Range-Error: bytes=0-100,200-300; multiple-ranges-not-supported

The requested range form is not supported.
```

**Требуется защищённое соединение:**

```text
TBIP/2.0 55 REQUIRE SECURE
Content-Type: text/plain
Content-Length: <error-body-length>

A secure connection is required.
```

### 4.6. Заголовки

**Заголовки запроса:**

| Заголовок | Описание | Пример |
|-----------|----------|--------|
| `Range` | Один запрашиваемый диапазон байтов | `Range: bytes=100-500` |

**Заголовки ответа:**

| Заголовок | Описание | Пример |
|-----------|----------|--------|
| `Content-Type` | MIME-тип возвращаемых данных | `Content-Type: image/png` |
| `Content-Length` | Количество байтов в передаваемом теле | `Content-Length: 12345` |
| `Content-Range` | Возвращённый интервал байтов и полный размер источника | `Content-Range: bytes 100-500/12345` |
| `FILE-SHA256` | SHA-256 хеш полного исходного файла | `FILE-SHA256: <sha256>` |
| `SOURCE-CONTENT-LENGTH` | Размер полного исходного файла в байтах | `SOURCE-CONTENT-LENGTH: 12345` |
| `Last-Modified` | Дата последнего изменения исходного файла | `Last-Modified: 2024-06-12` |
| `Location` | Новый путь для ответа `21 MOVED` | `Location: /media/new-logo.png` |
| `Range-Error` | Запрошенный диапазон и причина, по которой он не может быть предоставлен | `Range-Error: bytes=20000-21000; outside-source` |

### 4.7. Поведение сервера

1. Принять TCP-соединение на порту `81` по умолчанию.
2. Определить, используется ли TLS, SSH или незашифрованный запрос, а затем применить политику безопасности сервера.
3. Если требуется защищённое соединение, а запрос не зашифрован, вернуть `55 REQUIRE SECURE` и закрыть соединение.
4. Прочитать строку запроса и заголовки.
5. Проверить версию TBIP. Если версия не поддерживается, вернуть `51 VERSION NOT SUPPORTED`.
6. Если метод — `GET` или `HEAD`:
   - Искать файл с точно указанным именем; не добавлять расширение автоматически.
   - Если ресурс существует, определить его тип содержимого и вернуть соответствующие метаданные.
   - Для `GET` отправить тело ресурса. Для `HEAD` отправить заголовки ответа без тела.
   - Если в запросе `GET` присутствует один корректный `Range`, вернуть запрошенные байты и метаданные `Content-Range`.
   - Отклонить запрос с несколькими диапазонами кодом `54 UNSUPPORTED RANGE`.
   - Если ресурс не существует, вернуть `31 NOT FOUND`.
   - Если путь указывает на каталог, вернуть `31 NOT FOUND`; TBIP по умолчанию не преобразует каталог в индексный файл.
7. Если метод не `GET` и не `HEAD`, вернуть `50 METHOD NOT ALLOWED`.

`Content-Length` всегда описывает передаваемое тело ответа. Chunked transfer не используется. Клиент считывает ровно `Content-Length` байтов.

## 5. Работа TNet

Сначала клиент использует UTNP, чтобы обнаружить endpoint и версию необходимого протокола передачи содержимого. Затем он открывает отдельное TCP-соединение с объявленными хостом и портом этого протокола.

Пример получения документа TMkUp:

```text
Клиент подключается к endpoint UTNP на порту 34
  |
  |-- UTNP/2.0 NEGOTIATE tmutp
  |   Supported-Versions: 1.0,2.0
  |
  |<-- UTNP/2.0 START PROTOCOL tmutp 2.0 example.com 100
  |    Security: tls,ssh
  |
  |-- закрывает соединение UTNP
  |
  |-- подключается к example.com:100, используя транспорт,
  |   который принимает сервер
  |-- TMUTP/2.0 GET /index.tmkup
  |
  |<-- TMUTP/2.0 20 OK + документ TMkUp
```

Если документ ссылается на бинарный ресурс, клиент отдельно согласует TBIP:

```text
Клиент подключается к endpoint UTNP на порту 34
  |
  |-- UTNP/2.0 NEGOTIATE tbip
  |   Supported-Versions: 1.0,2.0
  |
  |<-- UTNP/2.0 START PROTOCOL tbip 2.0 example.com 81
  |    Security: tls
  |
  |-- закрывает соединение UTNP
  |
  |-- подключается к example.com:81, используя транспорт,
  |   который принимает сервер
  |-- TBIP/2.0 GET /logo.png
  |
  |<-- TBIP/2.0 20 OK + бинарные данные изображения
```

При выборе TLS, SSH или незашифрованного транспорта клиент должен применять собственную политику безопасности. Значение `Security`, полученное через UTNP, носит информационный характер и не заменяет транспортный handshake.

## 6. Краткое описание версии 2.0

Основные дополнения и изменения в TNet Protocols 2.0:

- UTNP поддерживает согласование одного протокола за запрос с помощью `Supported-Versions`.
- Ответы UTNP `START PROTOCOL` и записи `AVAILABLE` содержат список `Security`.
- В UTNP добавлена команда `EXPLORE`, возвращающая известные или рекомендованные узлы UTNP.
- UTNP, TMUTP и TBIP могут работать через TLS, SSH или незашифрованный TCP на одном и том же порту соответствующего протокола — с учётом политик клиента и сервера.
- TMUTP и TBIP содержат метаданные исходного файла, включая `FILE-SHA256` и `SOURCE-CONTENT-LENGTH`.
- TMUTP и TBIP поддерживают запросы диапазонов байтов и определяют связанные с ними коды состояния `52`, `53` и `54`.
- Код состояния `55` означает `REQUIRE SECURE`.
